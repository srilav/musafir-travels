▸ Claude’s response

Here's a plain-language walkthrough of each choice, what it actually does, and what else was on the table.

React + TypeScript — the UI framework

What it is: React is a library for building UIs out of reusable pieces called "components" (e.g., a TripCard component you use once per trip). TypeScript is JavaScript with type annotations, so the editor/compiler catches mistakes like "you forgot this field" before you run the code.

Why it matters here: Most day-to-day frontend work — forms, lists, screens — happens by composing components. TypeScript is especially useful when a frontend and backend need to agree on data shapes (your api-contract-spec.md).

Alternatives: Vue (similar idea, gentler learning curve for some), Svelte (compiles away a lot of the boilerplate, smaller bundles), Next.js (React, but with server-rendering and routing built in — more powerful, more setup than a weekend needs), plain JavaScript instead of TypeScript (less safety, less typing overhead).

Vite — the build tool

What it is: The tool that turns your source code into something a browser can run, and gives you a local dev server with instant reload while you code.

Why it matters here: It's just infrastructure — you don't interact with it directly much, but it's what makes npm run dev fast.

Alternatives: Create React App (older, slower, effectively deprecated), Webpack directly (much more manual configuration), Parcel (also zero-config, less popular now).

Tailwind CSS — the styling approach

What it is: Instead of writing separate .css files with class names like .trip-card, you style elements by stacking small utility classes directly in the markup, e.g. <div className="p-4 rounded shadow">.

Why it matters here: Fast to build with because you never switch files or invent class names — good fit for a solo weekend build where speed beats architectural purity.

Alternatives: Plain CSS / CSS Modules (more traditional, more files, slower to iterate), a component library like MUI or shadcn/ui (pre-built buttons/forms/modals — faster if their look fits your needs, slower if you fight the defaults), styled-components/CSS-in-JS (styles live in your component files as JS).

React Router — navigation between screens

What it is: Maps URLs (/login, /trips, /trips/123) to which component renders. Without it, a React app is just one page with no shareable URLs or back-button support.

Why it matters here: You have 3 screens (login, trip list, trip planner) that need distinct URLs.

Alternatives: Since we picked plain React + Vite (not Next.js), React Router is the de facto standard — the main alternative would have been adopting Next.js instead, which bundles routing in.

TanStack React Query — talking to the backend

What it is: A library that manages the lifecycle of server data — fetching it, caching it, refetching it when it's stale, tracking loading/error states — so you don't hand-write that logic yourself.

Why it matters here: Every screen shows data from the API (trip list, trip detail). Without it, you'd manually write useState + useEffect + loading flags for every single fetch, which turns repetitive fast.

Alternatives: Redux Toolkit (a general-purpose global state store — much more boilerplate, better suited to complex client-side state than "fetch this JSON from the server"), plain fetch/useState/useEffect with no library (zero dependencies, but you write and re-write the same loading/error/cache logic by hand each time), SWR (a smaller library very similar to React Query).

Client-side PDF generation

What it is: The itinerary PDF gets built in the browser using a JS library (e.g. jspdf), rather than the server generating and returning a file.

Why it matters here: No backend endpoint or PDF-generation dependency needed — one less moving part for a solo weekend build, since all the itinerary data is already loaded in the browser.

Alternatives: Server-side generation (backend renders the PDF, e.g. with a headless-browser tool like Puppeteer, and returns it) — produces more consistent, print-perfect output and can be reused (emailed, regenerated later) without the browser, but adds an API endpoint and a server dependency.

The common thread: every choice trades a bit of "best possible" for "fastest to build correctly, solo, in a weekend" — which matches the constraint you set in goal-spec.md. If the project grows past the weekend (more screens, a team, a real design system), Tailwind → component library and React Query → Redux are the two most likely places you'd reconsider.

what is JWT expiry?

▸ Claude’s response

JWT expiry is a timestamp baked into the token itself (the exp claim) that says "this token is only valid until this moment."

How it works: When the backend issues a JWT at login, it signs in a payload like {"user_id": "...", "exp": 1234567890}. On every subsequent request, the backend checks that timestamp — if the current time is past exp, it rejects the token with a 401, even though the token's signature is still technically valid. There's no server-side "logout this token" list by default; expiry is the only built-in way a JWT stops working.

Why it matters for this app: In the spec I wrote JWT_EXPIRY_MINUTES and suggested ~7 days. That means after logging in, you stay logged in for 7 days without re-entering your password — then the token stops working and the frontend's 401 handler (already in frontend-spec.md) kicks you back to /login.

The tradeoff behind the open question I flagged:

  • Short expiry (e.g. 1 hour) is more secure — a leaked token is only useful briefly — but annoying, since you'd need a "refresh token" flow to silently renew it, or you'd get logged out constantly. We haven't built a refresh flow.
  • Long expiry (e.g. 7–30 days, or no expiry at all) means you rarely have to log in again, which fits a personal single-user app — but a leaked token stays valid longer, and there's no way to force-expire it early (no refresh flow = no easy revocation) short of rotating JWT_SECRET, which would log out everyone.

Given this is a personal weekend app with no sensitive payment/PII data beyond your own trip plans, 7–30 days without a refresh flow is a reasonable tradeoff — that's why I flagged it as a confirm-or-adjust open question rather than a blocker. Want me to pick a specific number and lock it in, or leave it open for now?

Yes, AWS is entirely possible — it's just a different tradeoff than Railway. If you want to stay on AWS, the closest equivalent to "one project, API + DB, minimal config" would be AWS App Runner (managed container hosting) + RDS for PostgreSQL (managed database), rather than raw EC2 or Lambda.

Pros of AWS:

  • Industry-standard skill — more transferable experience than a boutique PaaS like Railway, which matters if this is for learning/portfolio purposes
  • Much more generous free tier (RDS/EC2 free for 12 months) and far more headroom if this app ever needs to scale beyond a weekend toy
  • More control over networking, security, and infra if the project grows

Cons of AWS:

  • Meaningfully more setup: you're now configuring a VPC, security groups, an RDS instance, IAM roles, and a deploy pipeline (App Runner from ECR/GitHub) — versus Railway's "connect repo, add Postgres, done"
  • That setup overhead directly eats into a 1-person/1-weekend timeline — this is the main reason I recommended Railway in the first place
  • Slightly more moving parts to debug when something doesn't connect (e.g. security group blocking RDS access) — a common first-timer AWS trip-up

My take: if the weekend timeline is a hard constraint, Railway still gets you building sooner. If part of the goal is learning AWS specifically (plausible, given this looks like a teaching context), App Runner + RDS is the right AWS-native pick and I'd steer you away from raw EC2/Lambda for a first pass.

Key Technical Decisions (filling gaps the specs left open)

  • SQLAlchemy: sync Session + psycopg (v3) driver, run in FastAPI's threadpool. Async SQLAlchemy adds real complexity with no benefit at single-user scale.
  • JWT library: pyjwt (more actively maintained than python-jose, which has had algorithm-confusion CVEs).
  • Password hashing: the bcrypt package directly (bcrypt.hashpw/checkpw), not passlib — passlib is unmaintained and breaks noisily with bcrypt>=4.1.
  • trip_type: SQLAlchemy Enum(..., native_enum=False) → VARCHAR + CHECK constraint, not a native Postgres ENUM — easier to add a trip type later without an ALTER TYPE migration.
  • created_at serialization: api-contract-spec.md specifies a trailing Z (e.g. 2026-09-16T10:00:00Z); Pydantic v2 defaults to +00:00. Add an explicit serializer so the contract is matched exactly.
  • Day-generation transactionality: Trip + its N Day rows are built in one service function and committed in a single transaction — a partial Trip (missing Days) must never be persisted.
  • Ownership-check pattern: every query filters id == X AND user_id == current_user.id together (never fetch-then-compare-then-403), so "not found" and "not yours" are structurally the same 404 path.
  • Cascade delete: both the SQLAlchemy relationship (cascade="all, delete-orphan") and the DB-level FK (ON DELETE CASCADE).
  • Testing DB: real Postgres via docker-compose for backend tests, not SQLite (SQLite's weaker constraint semantics could mask Postgres-specific bugs).
  • PDF export: jspdf alone (no html2canvas) — the spec wants a plain text list, not a styled DOM screenshot.
  • CORS for Vercel previews (flag for Phase 6): FastAPI's CORSMiddleware.allow_origins is exact-match only — *.vercel.app needs allow_origin_regex (e.g. r"https://.*\.vercel\.app") in addition to the exact production domain.
  • Same Docker image for API and migrations: the ECS one-off migration task and the API service run the same image with a different container command (alembic upgrade head vs uvicorn ...), so migrations always match deployed code.
